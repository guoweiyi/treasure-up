## 已落地的主要行为

| --- | --- | --- |

| UP 与收藏 | 已知域名链接解析、独立来源类型、首次处理策略、增量窗口、周期全量、检查历史和新增计数 | 不用单一时间水位判断新视频；区分初次发现与真正新发布 |

| 客户端 | 安装式 Web 应用、独立系统 WebView 客户端工程、服务地址识别接口、平台构建流程 | 服务端一份数据，多终端连接；不复制采集引擎到手机 |

## 保持轻量的取舍

前台共用 Vue 界面，播放器及后台按路由加载；HLS 代码按需导入。系统 WebView 壳不捆绑完整 Chromium，也不在客户端携带 Python、数据库或 FFmpeg。Docker 仍保留 PostgreSQL、Redis 和备份边界；轻量模式减少进程而非用不可靠的内存队列代替持久状态。当前未进行多万条资料库压测，不给出未经测量的内存与起播速度承诺。

无损分片不降低原始音视频码率，完整观看所需字节不会凭空减少。节省来自按需加载、限制预缓冲和减少反复下载；画质、音质不靠自动降级换取。HDR / 杜比 / 空间音频仍需要对应设备验证。

## 明确的后续验收

- 源站：本轮新增自动检测使用夹具验证，没有用真实 Cookie 发起批量扫描。先用低频小来源分别验证 UP 和收藏夹，再扩大规模；间隔配置不保证不会风控。
- 对象存储：仍需独立 S3 / OSS prefix 的 CORS、Range、签名续期与中断恢复实桶测试。
- 通行密钥：签名和攻击场景自动化测试与真实设备登记是两件事；Windows Hello、Touch ID、Android 和 iOS 需分别登记、登录、撤销验证。
- 多平台：构建成功不等于安装、播放、休眠恢复、音视频输出和商店审核完成。Apple 签名、公证、配置描述文件与应用关联域名需要发布账号。工程不会伪造可用的商店版本。
- 扩展来源：稍后再考虑合集 / 稍后再看 / 番剧等适配器；当前明确支持 UP 投稿与收藏夹，不把任意网址当作可用采集源。
- 已有稿件变化：来源新条目检测不等于已保存稿件新增 / 修改分 P 的实时同步；当前统计刷新也不会重下载已有媒体，变更多 P 仍需明确的重新采集任务。
- 大规模运行：需长时间调度、数万视频检索、低内存机器和高延迟云节点测试，再决定是否拆分原生播放器内核或替换任务组件。
