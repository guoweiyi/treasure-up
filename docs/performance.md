# 页面与播放性能

本轮优先处理用户打开页面到视频起播的等待链，不增加转码服务、额外缓存数据库或客户端框架。原始音视频规格保持不变，兼容副本仍由用户明确选择。

## 请求与首屏

- 播放器不再等待整包弹幕下载、解析后才请求媒体。弹幕异步加入当前播放器；切换视频、分 P 或身份后，过期结果不能覆盖新播放器。
- Artplayer 与弹幕引擎按需加载，与播放会话请求并行。视频页主模块从 279.68 KB 降至约 83.39 KB；分拆后的引擎在实际播放页加载，不能把模块拆分说成总依赖消失。
- 恢复进度提前并行读取，有独立取消与时间预算；已知有效进度作为 HLS 起始位置。慢进度接口不会无限阻塞视频，也不会在用户已经播放后突然跳回。
- 首页、UP 主视频、相关推荐和来源播放列表使用可选 `view=card`。卡片响应保留标题、封面、UP、统计、个人片单状态、采集状态与内容标识，不携带长简介、全部原站格式和逐版本媒体探测记录。默认 `view=full` 以及详情接口保留兼容。
- 采集状态投影只从作业 JSON 提取相关键，不再为展示状态加载评论候选、分页历史和素材工作清单。

## 分发与后台任务

- 创建播放会话复用同一次完整副本列表与路线观测，避免重复查询。
- 正常分片读取逐次检查会话归属、期限、授权资产及存储状态，但不持有同一播放会话的写锁等待存储 HEAD。故障切换才取锁并重新读取状态，防止两个分片同时故障时重复切换。
- 同一媒体准备任务的响度分析、HLS 封装共享一次物化并完整校验的临时源，减少一次整文件下载或复制。临时源不跨任务缓存，身份或文件状态变化会拒绝复用；成功、失败和取消都清理。已有分析和分片成果均可复用时不产生临时副本。
- 完成的响度分析通过已有任务租约保护单独提交，后续包装失败不再回滚已完成的分析；取消或更换任务所有者仍阻止提交，避免重试反复解码长音轨。
- 修复 HEVC＋FLAC 原档被 HLS 白名单拒绝的问题。仅增加已验证的 FLAC 无损封装，保持原 `strict=unofficial` 和 `-c copy`；校验 STREAMINFO、位深、采样率、声道及完整音视频包摘要。两路摘要在同一次读取中计算，不在生产包装里重复解码 PCM。杜比与 EC-3 的封装参数保持原样。
- NGINX 复用上游 HTTP 连接；DNS 解析和连接建立分别有 2 秒与 3 秒预算。保留 Docker 动态解析以适应 API 容器更换地址。网页健康检查经过完整代理链路，单独的 API 健康不代表网页代理可达。
- 内容哈希命名的 JS / CSS 在镜像构建时预压缩，浏览器协商 gzip，使用长期 immutable 缓存。API、会话、视频资产不加入公共缓存，也不对已压缩视频重复 gzip。[NGINX gzip_static](https://nginx.org/en/docs/http/ngx_http_gzip_static_module.html)、[上游连接复用](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)
- 后台工作进程设置相对 CPU 权重 256，在 CPU 争用时给默认权重 1024 的 API、Web 留出优先级；这不是 CPU 硬上限，空闲时仍能利用资源，也不是磁盘带宽限速。

## 测量方法与边界

2026-10-05 在本地 8 条视频库测量。开始时外部 `/health` 超过 15 秒仍未返回，而 API 内部相同请求约 27 毫秒；NGINX 同时记录 Docker DNS 解析超时。平滑重载恢复后，优化前暖态列表与详情接口五次测量中位数约 35.65 / 22.09 毫秒；播放会话约 192 毫秒，首片 64 KiB Range 约 115 毫秒。此前单次 10.79 秒会话与 1.39 秒 Range 属于抖动样本，不能用来宣称代码获得几十倍加速。

同一视频库更新后的实际 HTTP 测量：

| 项目 | 更新前 | 更新后 |
| --- | ---: | ---: |
| 首页 8 条视频列表响应 | 72,124 B | 11,777 B，减少 83.7% |
| 入口 JS / CSS 传输 | 177,273 B | 59,676 B，减少 66.3% |
| 列表五次请求中位数 | 35.65 ms | 47.25 ms |
| 详情五次请求中位数 | 22.09 ms | 28.10 ms |
| 播放会话创建，单次 | 191.97 ms | 68.88 ms |
| 清单请求，单次 | 8.90 ms | 10.73 ms |
| 首片 64 KiB Range，单次 | 114.56 ms | 14.92 ms |

入口两个文件均实际协商到 `Content-Encoding: gzip`，不是构建报告中的估计值。列表和详情耗时未显示稳定改善；播放链单次值也不能外推成稳定加速比例。此次可确定的收益是网络负载、重复工作和串行等待减少，不能宣称所有场景首帧或持续带宽都得到同样改善。

后台监控中数 GB 的容器内存主要是 Linux 文件页缓存：抽样匿名内存约 173–189 MB、Celery 子进程 RSS 约 106–146 MB，未出现 OOM。不能由 Docker 的单项内存数字认定 Python 泄漏，更不能为此清空系统页缓存或终止正在采集的视频。

本次更新期间 Docker Linux 环境的 I/O pressure `full avg10` 一度达到 92.69%，隔离测试也出现小文件 fsync 等待超过 30 秒。测试数据迁至独立 tmpfs PostgreSQL 和临时目录后，最终 638 项后端回归在约 101 秒完成；没有修改业务 PostgreSQL、fsync 或原始资产。这说明宿主 I/O 争用是此次慢响应的重要环境因素，页面缩包不能独自消除这种卡顿。

真实两 P 长视频 `BV1r4a96KEfn` 的 HLS 恢复任务均首次成功，分别生成 709 / 763 片。保留 4K HEVC 视频及 24 bit、48 kHz、双声道 FLAC；封装前后完整音视频压缩包摘要和 FLAC STREAMINFO 校验通过。恢复时只复用与当前源资产、分析版本、目标响度和完整结果相匹配的既有分析，并记录审计日志，没有重新下载原档。

访客播放会话、清单与首片 64 KiB Range 的组合请求均返回成功（Range 为 206）；后台包装完成后两 P 的单次组合耗时约 44.39 / 49.94 毫秒。但 P1 同一链路在 P2 后台复制期间曾耗时 13.07 秒。这些是不同负载下的抽样，不是稳定首帧指标，也说明此次仍未消除宿主磁盘争用导致的等待。

HLS 无损分片必须服从源视频关键帧。配置 6 秒不代表每片恰好 6 秒，更小分片也不能消除高码率所需带宽。真实杜比样本约 21–23 Mbps，20 Mbps 的持续链路无法靠缓冲设置保证无卡顿。证据与后续实验门槛见[分片研究记录](performance-segmentation.md)；Apple 设备是否真正输出 Atmos 仍需要对应硬件验证。

## 验证

- 最终后端完整回归：638 项通过，7 项因未挂载私有媒体样本跳过；包含真实 PostgreSQL 并发、备份迁移测试。新增 FLAC 支持未改变原有杜比封装参数。
- 前端：109 项通过，类型检查与生产构建成功。新增覆盖慢弹幕、过期结果、慢进度和 HLS 起始位置。
- 部署：105 项通过、8 项环境条件跳过；另行显式运行的真实 NGINX 隔离测试 4 项全部通过。压缩协商、缓存隔离和请求限制已接入 GitHub Verify 流水线。
- 本地浏览器：杜比原档恢复到约 184 秒；AAC 副本持续播放至 251 秒并验证跳转；充电 AV1 长视频恢复并播放。修复后的两 P 4K HEVC＋FLAC 长视频均确认使用浏览器原生 HLS（709 / 763 片），续播、切 P 与中段跳转通过：P1 从约 2129 秒继续播放至 2161 秒，P2 跳到约 2292 秒时媒体 readyState=4、无解码错误。未进行全片连续观看、物理音频试听或 Apple 真机验收，不能据此宣称所有场景无卡顿。
- 390 px 窄屏下内容标识正常折行，无横向溢出。这是桌面浏览器尺寸检查，不是 iOS 真机验收。
