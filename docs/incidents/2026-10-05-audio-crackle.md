# 2026-10-05 间歇音爆与滋滋声排查

用户设备为 macOS 网页和 App，症状是多条视频偶发、分段出现音爆或滋滋声。目前没有取得用户明确指出的异常视频及时间点，也没有连接 Mac 实机。以下区分代码缺陷、合成复现与尚未证实的现场原因；不能将回归通过当作用户听感问题已解决。

## 已复现的问题

### 多声道转 AAC 的下混超幅

`backend/app/ingest/media.py` 的声音兼容版及普通 SDR 转码均仅以 `-ac 2` 指定立体声。浮点混音会叠加相关声道，原始各声道没有超幅也不代表下混后安全。

使用项目现有 Windows FFmpeg 6.1.1 生成 3 秒干净 5.1 EC-3：各非 LFE 声道为同相、幅度 0.7 的正弦。源音频解码样本峰值为 −3.086 dBFS，按旧参数生成的 AAC 为 **+4.729 dBFS**。这是终端输出削波的风险，尚非用户指定视频的噪声复现。显式 `aresample=out_chlayout=stereo:rematrix_maxval=1` 后，同一样本为 −2.276 dBFS。

修复使两个转码分支显式归一化下混并预留 1 dB 编码余量。原档仍保留。新副本使用 v2 格式标识，显式生成任务使用 `compatible-v3`；不会误复用旧下混产物，也不会删除旧版本或恢复已暂停任务。AAC 快捷入口优先选择同一原档的新版，画质列表区分新旧声音副本。固定余量及合成峰值测试不构成所有素材的真峰值限制器，不能修复源音轨内本来就有的失真。参数依据见 [FFmpeg 重采样/声道重混文档](https://ffmpeg.org/ffmpeg-resampler.html#Resampler-Options)。

### 解码错误被成功退出码掩盖

旧 `_run_ffmpeg` 丢弃 stderr、仅依据进程退出码。对 5 秒 AAC 的第 100/236 帧注入损坏后，转码报告 `Error decoding AAC frame header`，但退出码为 0，仍输出兼容副本。本地 FFmpeg 6.1.1 对该样本添加 `-xerror` 仍可能退出 0，只提前截断输出。因此仅补 `-xerror` 不够。

修复为严格处理 `-v error` 的有界诊断输出，错误即拒绝发布，不把私有路径及原始日志返回前端。播放工具同样增加显式严格模式；响度测量正常使用 stderr 的调用仍可工作。FFmpeg 参数语义见 [官方文档](https://ffmpeg.org/ffmpeg.html)。

## 全链路检查

| 环节 | 结果与处理 | 证据边界 |
| --- | --- | --- |
| 采集选流/下载 | 获取源音轨；拒绝跳过缺失下载片段 | 源站文件可能已有听感失真；下载完成不等于音频干净 |
| 原档合并 | `-c copy`；杜比相关验证包含包摘要及信令；新采集原档发布前完整解码音轨 | 不会自动重新扫描已有原档；独立本地导入入口仍采用元数据探测，可先用离线诊断检查 |
| AAC 兼容转码 | 修复下混超幅与错误日志被忽略 | 既有副本不会因代码更新而自动修复 |
| HLS 分片 | 保持 stream copy；把原先限于 FLAC/EC-3/DOVI 的包验证扩展到普通 AAC/AC3及无音轨视频 | 包哈希证明压缩内容未改变，不证明 PCM 听感；生产任务尚未逐包验证时间戳，合成跨片时间轴已有实测回归 |
| EC-3/JOC 修复 | 修改初始化容器信令，另行验证压缩包 | 未发现直接修改波形的逻辑；不等于全面满足 Apple HLS authoring profile |
| 响度分析 | 输出 null，记录建议衰减；播放音量平衡默认关闭且不放大 | 可选播放衰减不能代替正确下混 |
| 存储 | 入库 SHA-256 与大小，上传后读回核验；媒体处理前 materialize 再校验 | 没有对用户此次异常的实际 CDN 响应抓包 |
| HTTP/Range/Nginx | 本地 FileResponse/X-Accel 或云端直链，未见音频重写 | 断网、链接续期换源可造成中断，不能据此认定分段滋滋声来源 |
| 网页播放器 | HTMLVideoElement / 原生 HLS / hls.js；没有 AudioContext、PCM 或 Web Audio 重采样 | 杂音通常不会产生媒体错误事件，自动回退不一定触发 |
| macOS App | Tauri WebView 加载同一站点，无独立音频 DSP | 网页与 App 共享部分播放链，二者异常不足以断定采集损坏 |

HLS 哈希校验同时读取音视频，每个输入一次，避免杜比路径分别多次扫描同一文件。对普通 AAC 增加全流读取会增加准备阶段 I/O，发生在媒体处理任务中。既有 HLS 缓存不会因此自动重建或获得新的验证结论。

## 现场对照方法

播放器设置增加「播放方式 → 文件直读」，保留同一版本、音轨和画质，沿用现有进度及播放状态恢复流程；可切回「自动选择」。它不需要先等待浏览器报错。

1. 在同一音量、1× 播放速度下，记下视频/BV号、分 P、播放版本、时间点和输出设备，重复播放相同片段。
2. 同一版本在自动/HLS 和文件直读之间对照。仅 HLS 异常时优先看封装、时间戳及系统 HLS 解码；二者均异常仍需核对源文件和终端。
3. 如已保存对应原档的 AAC 声音兼容版，再手动对照原音轨与新兼容版。旧兼容版不能用来验证新下混参数。
4. 对明确异常文件运行只读全音轨诊断，并在 Mac 上用同一文件对照。Safari、Chrome、App 的结果及扬声器/耳机/HDMI 输出应分别记录。FFmpeg 解码正常无法排除浏览器或系统输出问题，也无法识别所有已经编码进源音轨的杂音。

这轮不重采、删除或覆盖业务媒体，不部署服务或修改 Mac 系统音频设置。现有未提交的存储/路由工作保留。

## 只读离线诊断

新增 `backend/scripts/audio_diagnose.py`，仅依赖 Python 标准库及 FFmpeg，不连接业务数据库。它逐音轨完整解码，报告浮点样本峰值、样本数、时长、解码错误类别和可选输入文件 SHA-256；不输出文件名、签名 URL 或原始工具日志。可一次传入多个本地文件，JSON 中的 `input_1` 等按参数顺序对应输入。HLS 仅接受本地清单及本地引用；其输入 SHA-256 只覆盖清单本身。

```bash
python backend/scripts/audio_diagnose.py /path/original.mp4 /path/aac-copy.mp4 /path/index.m3u8 --sha256 > audio-report.json
```

全轨扫描现有参考素材（非用户此次指定的故障样片）：

| 本机参考样片 | 音频 | 浮点样本峰值 | 扫描结果 |
| --- | --- | --- | --- |
| `.tools/dolby-failure/source.m4a` | EC-3 7.1，331.936 秒 | −2.081 dBFS | 全轨解码成功，无 NaN/Inf |
| `.tools/dolby-reference/samples/audio.m4a` | EC-3 | −3.630 dBFS | 全轨解码成功，无 NaN/Inf |
| `data/sample/video.mp4` | AAC | +0.566 dBFS | 全轨解码成功，无 NaN/Inf；存在超过满幅的浮点样本 |

AAC 解码可能产生超过满幅的浮点样本；这一测量本身不能证明已发生可闻削波，还取决于解码输出、音量及设备链路。没有用户噪声时间点，因此不能据此确定此次故障原因。该扫描不修改参考素材，私有样片及原始报告留在忽略目录。

Docker 无网络、代码只读挂载，仅使用临时数据库/数据目录，未挂载业务媒体。9 项跳过为 7 项需要显式私有杜比素材的测试与 2 项 PostgreSQL 专项；离线音频扫描不能替代这些跳过项。临时目录和 FFprobe 可选字段导致的新增测试夹具错误已修正，最后完整定向运行无失败。

`test_hls_audio_timeline.py` 实际生成两份 7 秒素材，各跨 4 个 HLS 分片。AAC 的 **330 个音频包**、EC-3 的 **219 个音频包**顺序和逐包哈希一致；相对 PTS/DTS 完全一致，中间帧连续。两者时间轴整体均偏移 `119/1500` 秒，测试允许整个轨道统一偏移，不掩盖中段跳变。AAC HLS 首包未报告 duration，明确记为 null；其余 328 个中间包时长和相邻时间戳均经过精确分数比较。AAC/EC-3 首包 skip-samples 信息及 AAC 尾包时长在 MP4/HLS 间存在封装差异，已记录而未冒充完全相同；该测试不验证 Mac 解码听感、首尾裁剪或完整音画同步。

部署新代码后，旧兼容副本需要通过管理员现有「生成兼容副本」入口显式生成新版，才会使用修正的下混参数。本轮未执行该业务操作，也未重新部署。
