## 故障一：评论素材账本中的 Decimal 不能写入 JSON

### 触发链

1. 《窗》的评论分页已经结束：检查点记录 `roots_done=true`、`source_end=true`、`scanned=125`，但没有 `selected`，说明失败发生在候选落库阶段。
2. 部分候选作者此前已有归档头像。保存评论后，素材预算需要将这些既有资产计入库存，避免刷新后绕过累计素材上限。
3. `runner._comment_ledger()` 使用 `SUM(Asset.size)` 汇总既有素材大小。`Asset.size` 是 `BigInteger`；PostgreSQL 的该汇总由 psycopg 返回 `Decimal`。
4. 汇总值未经转换便写入 `video.metadata_json.comment_assets` 及检查点账本。后续 ORM 查询触发 autoflush，JSON 编码抛出 `TypeError`，导致该批评论事务回滚。
5. 同一检查点重试仍会遇到同一数据形状，直到重试额度耗尽。因为它是未分类的 Python 内部异常，而不是已有的可处理评论组件错误，执行没有走到创建媒体子任务的分支。

真实安全诊断定位到 `run_job → _archive → _comments → comment_capture.collect → _save_comment`，最后一处是触发 autoflush 的查询。异常发生在客户端参数 JSON 编码阶段，尚未发送有效 SQL，因此 PostgreSQL 服务端没有对应 ERROR 日志并不能排除此类故障。

### 为什么 SQLite 测试没有发现

同样的 `SUM(size)` 在 SQLite 中返回普通整数，能够写入 JSON。125 条真实候选在 SQLite 重放成功；带既有作者头像资产的 PostgreSQL 隔离重放则稳定失败。只有合成评论、没有既有头像库存的测试也不会进入产生非零 legacy 账本的分支。

本次新增 PostgreSQL 回归保留了关键组合：**已存头像资产、复用该头像的评论作者、含行内表情的候选、真实 ORM flush 与检查点提交**，不依赖真实用户数据或网络请求。

### 修复

- 在 [`runner._comment_ledger`](../../backend/app/ingest/runner.py) 构造账本前，将 `size` 和 `count` 显式转换为整数。资产大小与计数本身都是整数，不改变预算计算含义。
- 新增 [`test_ingest_comments_postgres.py`](../../backend/tests/test_ingest_comments_postgres.py)，验证候选成功落库、既有头像仍计入预算、检查点可序列化，重复执行不会新增重复评论或版本。
- 同类汇总检查：删除预检已做 `int(size)`；目录统计只经 API 的 JSON 编码器返回，不写 JSON 数据库列；其余整数表达式汇总未发现同一持久化问题。本次没有扩大修改这些路径。

## 故障二：原音轨含 JOC，但容器信令缺失，重试也未修复

### 触发链

下载结果中的音频原码流被识别为 `Dolby Digital Plus + Dolby Atmos`，但 MP4 的 EC-3 初始化信息 `dec3` 没有相应 JOC 配置。原程序正确拒绝将这个不一致结果作为已验证原档发布，报错为“EC-3 初始化信息缺少已检测到的 JOC 配置”。

该样本与此前只验证“合并时丢失容器标记”的案例不同：源音轨的容器自身也缺少 JOC 标记；原始码流包含 AC-3 核心及 dependent E-AC-3 帧。仅从源容器复制配置无法恢复缺失信息。另一方面，yt-dlp 重试时可能发现上一轮已完成的合并文件而跳过合并处理器，因此只修正合并处理器仍不能覆盖这条恢复路径。

### 修复与限制

- [`playback/ec3.py`](../../backend/app/playback/ec3.py) 增加有界原码流帧解析，按帧边界读取 E-AC-3 BSI / `addbsi` 中的真实 JOC complexity。拒绝截断、不支持或互相矛盾的结构，不扫描任意压缩字节来猜标记，也不按声道数猜 complexity。
- [`ingest/media.py`](../../backend/app/ingest/media.py) 在归档发布前校验中增加 `repair_scratch` 路径。仅允许修改 `scratch/downloads` 下尚未发布且非符号链接的临时文件；正常既有归档检查默认只读。
- 原码流采样限制为 10 秒、16 MiB，并保留进程超时与取消检查。确认真实参数后原子恢复容器信息，恢复前后比较音视频压缩包摘要；不重新编码、不将 E-AC-3 自动降为 AAC。
- 新下载和“已存在合并文件、重试跳过合并”的路径均走最终验证，因此都覆盖恢复。

离线故障样本测得 8 声道、JOC complexity 16。**16 是从该样本帧头读取的值，不是通用默认值，也不是扬声器数量。** 该验证证明信令与压缩载荷保持一致，不证明客户端或扬声器实际输出 Atmos。

这不是旧归档批量修复或迁移。已发布资产、原始样片不会被自动覆写；不支持的封装布局仍应失败并保留明确错误。

## 错误被旧进度和父任务成功状态掩盖

任务表已有终态失败，但视频 JSON 中可能仍保留上一阶段的 `running` / `queued` 提示。杜比案例的元数据父任务确实成功，却不能代表其媒体子任务成功。只显示父任务或旧视频提示会让用户看到“还在同步”或“已成功”，难以判断该重试哪个任务。

本轮由 [`capture_state.py`](../../backend/app/capture_state.py) 和 [`catalog.py`](../../backend/app/catalog.py) 在读取时综合最新元数据任务、媒体子任务与已登记原档，投射视频状态；不由队列终结器回写整个视频 JSON，避免覆盖另一个采集阶段刚提交的进度。后台父任务摘要包含独立媒体状态、子任务标识及可重试 / 可恢复信息。只有每个预期分 P 都存在登记原档，才将媒体状态视为完成；这项读取校验不额外探测源站或物理文件。

关闭媒体保存的任务仍可按其明确策略完成，充电等待不会冒充下载完成。任务详情提供媒体子任务的重试 / 继续入口，子任务排队或运行期间继续刷新，而不是在元数据父任务成功后停止观察。

此外增加两项诊断修正：

- [`ingest/diagnostics.py`](../../backend/app/ingest/diagnostics.py) 只记录异常类型、应用代码模块 / 函数 / 行号和摘要指纹，不记录异常原文、SQL 参数、局部变量、URL 或凭据。
- 通用异常先回滚，再重新读取已提交检查点后附加诊断。失败事务中新建的人物、图片任务或行 ID 不会被误保存。`LeaseLost` 原样交回队列层，不包装成可重试的内部采集错误，也不在失去租约后发布诊断或子任务。

本次没有增加“所有内部异常后仍派生媒体任务”的通用行为。先修复确定根因，保留元数据失败与检查点的真实语义。

## 已完成验证

### 恢复后追加发现的播放产物问题

原档恢复后继续验收，发现杜比视频的独立 `prepare_media` 任务在 HLS 声道核对阶段失败。完整 4K 样本的默认 HLS 探测只返回核心音轨的 6 声道，而原档及更充分的探测均为 8 声道。FFprobe 默认探测大小为 5,000,000 字节；扩大探测预算有助于识别分散在媒体中的信息，代价是更多读取与等待。[FFprobe 官方格式选项](https://ffmpeg.org/ffprobe-all.html#Format-Options)

修复仅针对 E-AC-3 分片首次探测的声道或布局不一致，再进行一次 32 MiB、10 秒分析预算的探测，进程仍受 120 秒超时和任务取消约束。后续声道、布局、编解码、DOVI、JOC、时长及完整音视频数据包哈希核对全部保留，没有放行“声道不一致”的例外。针对仍然缺少声道或音频包发生改变的反例继续拒绝发布。

另一个 `create_playback` 任务表示可选的 SDR 通用副本。当前实现不支持经验证的 HDR 色彩转换，因此对这一明确能力限制返回 `compatibility=unsupported`，后台显示“未生成兼容副本”，不再将其混同于原档采集失败；它也不创建虚假的副本标识。无损 HLS 由独立任务完成，其他实际转换错误仍按失败处理。

浏览器实际验收还发现：同一原档以文件方式能够播放，但该浏览器的 HLS 路径不能处理相同编码。旧播放器仅将原生媒体错误 `3` 视为媒体问题，将“不支持媒体”的错误 `4` 归到网络重试；加载阶段又丢失了分片错误类型。修复后每个分 P / 原档最多自动回退一次到**同一原档**的文件协议，并核对服务端返回的版本标识。进度、暂停、倍速、音量与首次自动播放意图均保留，旧请求不能覆盖新的播放选择；网络故障继续使用原有线路恢复逻辑。不能将“归档存在”直接等同于所有浏览器都能使用该分发协议。

## 同日后续：多视频回归与不支持 EC-3 的设备

用户要求进一步扩大测试并处理 iPhone、iPad、Mac 及不支持杜比音频的设备。本轮另外修复了多 P 断点恢复中的时间预算饥饿：每次续跑重复提交已经完成的弹幕阶段，可能在触及未完成评论前耗尽 45 秒切片。现跳过已完成阶段；模拟慢提交复现修前失败、修后推进。两 P 下载中第二 P 中断的回归验证恢复时不会重新下载第一 P。

EC-3 原档现在可生成独立的声音兼容副本：视频流复制，音频转换为 AAC-LC 立体声。发布前核对完整视频包摘要、DOVI 配置、色彩字段、分辨率、音轨格式与时长；任何不符都拒绝发布。原档保持不变。副本不带 Atmos 标记，也不会自动取代用户选中的版本。保留 HDR / Dolby Vision 视频并不等于将它转换为 SDR，也不保证旧设备具备其视频解码能力。新副本仍占用独立存储空间。

既有视频可在存储管理的原档行点击“生成兼容副本”；入口仅限管理员，重复请求复用作业，不重置暂停或失败状态。新声音副本按现有设置独立排队准备 HLS / 响度分析，资产、播放会话和分片不能混用原 Atmos 音轨。

播放器按实际文件 / 原生 HLS 与 MSE 路径分别查询解码能力，未知能力不拦截播放。对于不支持或未能确认 EC-3 的情况提供声音提示，以及指向同一原档已保存 AAC 副本的手动切换按钮。普通解码支持、空间呈现能力和实际输出状态分别处理；不会按 Apple 品牌、系统版本或连接耳机推定正在输出 Atmos。[W3C Media Capabilities](https://www.w3.org/TR/media-capabilities/)、[Apple HLS 音频要求](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/)

### 持续回归与验收边界

- `test_media_matrix.py` 在每次现有 Docker CI 全套测试中生成五种小视频：竖屏 H.264、HEVC、AV1、HDR10 + 普通 EC-3、无音轨视频。真实封装 HLS、核对音视频包摘要、解码并验证重复生成复用。合成 EC-3 明确不标为 Atmos。
- `test_audio_compatibility.py` 覆盖转换中改包、丢失 DOVI、色彩变化、非立体声、多音轨和异常时长；另外使用只读的真实 6 声道与 8 声道杜比样本，各取 3 秒验证 AAC 副本及其 HLS，视频包摘要、DOVI 和源文件哈希保持一致。这些私有样本没有加入仓库，CI 使用合成回归，私有回归在本机显式运行。
- `test_audio_compatibility_api.py` 验证管理员权限、重复请求、历史不支持结果保留、AAC 与原音轨的播放会话隔离。
- 本机未连接 Apple 真机，因此 iOS / iPadOS / macOS 的物理解码、AirPods / HDMI 路由及实际空间输出尚未验证。当前 HLS 仍是单 muxed media playlist，未实现完整 Apple multivariant master 的 JOC / Supplemental Codecs 信令；不能声称已全面满足 Apple HLS authoring profile。详见 [播放器设备说明](../../frontend/src/player/IOS_NOTES.md) 与 [杜比验证说明](../../backend/app/playback/ATMOS.md)。

通过新增管理员入口为真实 331.936 秒杜比原档生成 AAC 声音副本；`create_playback` 与独立的 `prepare_media` 均成功，后者同时完成 HLS 及响度分析。原档仍保留。

随后对该完整产物进行独立只读校验：原档 950,159,273 字节、AAC 副本 889,434,175 字节；**60 个唯一资产**（原档、副本、HLS index、init、56 个分片）的 SHA-256 和大小均匹配数据库。原档 SHA-256 匹配修复前固定基线；原档 → AAC → 完整 HLS 的全视频包摘要一致，AAC → HLS 的全音频包摘要一致。实际完整 DOVI 配置与 HLS init 均保留 DV 8.4 / level 10 / RPU；AAC 为 LC 双声道立体声，无 Atmos / EC-3 声明。副本的 HLS 来源确认为 AAC variant，文件首部 Range 206、清单 200 / 56 分片、首分片 Range 206 均通过。这 60 个资产与上文 458 个全库资产有交叠，不直接相加。
