## 修复的交叉复核

认证补丁最初对管理员更新目标使用 `FOR UPDATE`。交叉复核发现，两个管理员同时修改对方时，审计日志的操作者外键可能形成死锁。最终使用 `FOR NO KEY UPDATE`：仍与登录、重置串行，允许审计外键的 `KEY SHARE` 检查。新增真实 PostgreSQL 测试，让两个事务确实同时持有目标锁后写审计，验证密码更新、双方会话撤销和无关会话保留。该问题在本轮补丁复核中发现，不冒充基线漏洞。

CLI 重置和通行密钥注册也改用 `FOR NO KEY UPDATE`，避免与撤销密钥时的“删除会话 → 写入操作者审计外键”形成锁环。注册路径原本就存在这一问题，CLI 路径是此次增加锁后复核发现的回归。

存储登记最初的独占配置行锁会覆盖整段 HLS 上传，阻塞同节点的其他文件登记。最终采用 `FOR SHARE`，让上传者共享读取定位信息的保护；管理员配置写入使用非等待式咨询锁及 `NOWAIT` 行锁。目标节点或原默认节点繁忙时立即返回 409 并释放事务，避免管理请求持全局锁等待长视频上传。HLS 仍在完整索引和版本可发布时统一提交，未拆散原有原子发布事务。

来源恢复补丁另经“最近 N 个”窗口复核：首轮即为不可见条目记录窗口资格，恢复可见或列表重排不能扩大范围；真实新增的收藏 / 发布时间可以建立新的资格。新增回归覆盖收藏夹与 UP 来源，不把“事件未变的恢复”和“新收藏 / 新发布”混为一谈。

旧版本明确记录的 `initial_limit` 排除继续保留；旧不可见条目若没有保存首轮资格，不能根据后来变化的列表位置还原初始范围，因此保守排除，直到出现明确的新来源事件。不自动重扫或扩大历史归档范围。

锁兼容性依据：[PostgreSQL 显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)。SQLite 只承担普通单元测试，不作为跨进程锁语义的验证依据。

## 性能与体积边界

目录测试在冷 Session 中分别读取 1、24、100 条记录，计入总数及分页查询后，视频 / UP / 收藏夹 / 评论分别固定为 **7 / 4 / 4 / 6 次 SQL**。该数字不含鉴权查询及某些路由对父记录的存在性查询，不代表整个 HTTP 请求只执行这些语句。

弹幕合并的内存主要受单个解码片段大小影响，仍需读取一个完整片段；磁盘需要临时 SQLite、索引、输出 JSON 和一个片段的空间。HLS 缓存的 32 MiB 是原始索引字节预算，不是 Python 对象的精确内存上限。工具输出的 8 MiB 是轮询检测阈值，两次检测间可能短暂超出，并非操作系统硬配额。

**尚未解决的功能边界：** 合并弹幕超过 64 MiB 可以完成归档，但现有一次性弹幕读取 API 会拒绝并返回 503，前台不能完整展示该分 P 的弹幕。后续应增加按时间分段的弹幕交付和客户端窗口加载，不应直接移除服务端内存限制。本轮仅改进归档合并过程，不宣称已经支持超大弹幕全集播放。

没有增加常驻服务、模型或消息中间件。后台与播放器继续按路由加载；当前生产构建的入口 JS gzip 约 48 kB，后台 JS 约 142 kB，播放器页面约 69 kB，独立 HLS 库约 185 kB。后台 CSS gzip 约 49 kB。未删除 HLS、通行密钥或无损分片等必要依赖来换取表面上的体积下降。

`main.py`、后台主视图及采集执行器仍偏大，属于后续可维护性工作。下一轮应按明确的功能边界逐步拆分，并沿用此次回归；本轮没有进行缺少行为收益的大面积搬文件。
