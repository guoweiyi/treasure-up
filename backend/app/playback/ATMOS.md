# Preserving EC-3 / Dolby Atmos

The original EC-3 audio is kept as a stream copy. An AAC compatibility copy, when requested, is a separate asset. Selecting an EC-3 source but receiving AAC fails with `audio_codec_mismatch`; the archive does not silently substitute AAC for the selected original.

Two independent checks are needed:

- A bounded elementary-audio sample must be identified as Dolby Digital Plus + Dolby Atmos by ffprobe before `dolby_atmos` is true. Codec name or 6-channel audio alone is insufficient.
- The MP4 `ec-3/dec3` box must retain its JOC extension and actual `complexity_index_type_a`. This value can be 16 for a 6-channel stream; it is not inferred from the speaker count. New HLS initialization metadata records `ec3_configuration_verified`, and the muxed audio/video packet hashes must match the source.

## FFmpeg 7 workaround

The tested container uses FFmpeg 7.1.5. With the local authorized EC-3/JOC sample, its MP4/HLS stream-copy mux keeps the audio packets but drops the two-byte JOC extension from `dec3`. The [official June 2025 FFmpeg change](https://ffmpeg.org/pipermail/ffmpeg-devel/2025-June/344730.html) adds this signaling to the muxer; it is present in the [FFmpeg 8 muxer source](https://www.ffmpeg.org/doxygen/8.0/movenc_8c_source.html).

`ec3.py` therefore restores only this known extension, using the actual selected source track's configuration. Its destination is exclusively an unpublished scratch merge or new HLS `init.mp4`. It rejects unexpected box layouts, multiple audio configurations, mismatched substreams, invalid offsets and size overflow. A bounded sibling temporary file is verified before atomic replacement; cancellation leaves the original scratch input intact. Fast-start `stco`/`co64` offsets are adjusted, and compressed media bytes are unchanged. Existing archive assets are never destinations for this helper.

Some source tracks themselves omit the JOC extension: the observed 8-channel source combined an AC-3 core with a dependent E-AC-3 frame, while its `dec3` advertised only the core. For an **unpublished download scratch file only**, the archive verifier also walks complete AC-3/E-AC-3 frame boundaries in the existing bounded 10-second elementary sample and reads the actual JOC complexity from `addbsi`. The syntax follows [ETSI TS 102 366](https://www.etsi.org/deliver/etsi_ts/102300_102399/102366/01.03.01_60/ts_102366v010301p.pdf), with JOC extension semantics corroborated by the [FFmpeg header parser](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/ac3_parser.c). It rejects truncated frames, unsupported substreams and inconsistent complexity; it never scans audio payloads for marker bytes or assumes a fixed complexity. The scratch repair retains the muxer's substream layout and verifies both video and audio packet hashes before publication. It also runs when yt-dlp reuses a completed but previously unpublished merge and skips its merger callback.

After upgrading the pinned FFmpeg engine, remove the workaround only once actual sample tests prove that both MP4 merge and HLS initialization retain JOC and that both audio/video packet hashes remain identical. The helper already performs no rewrite when the muxer's output is correct.

## Old archives and operator checks

This change is not a migration. An old archive may contain Atmos packets but have lost JOC container signaling during an earlier merge. An existing `dolby_atmos: true` record may reflect the elementary sample only. It is not proof that the old MP4 or old HLS initialization has been repaired, nor that a user's output route renders spatial audio.

For a new capture, enable **管理中心 → 系统设置 → 优先杜比全景声原档** (or the corresponding source policy), use an account that can access the complete source, and inspect the media task result. Retrying a failed merge before its archive was published runs the guarded merge again. `dolby_metadata_missing` means the elementary Atmos evidence and container signaling disagree; the failed output is not published. HLS preparation uses a new `hls-copy-v2` format key and verifies the newly generated initialization; old packages remain unchanged.

If an old published MP4 has already lost the extension, merely retrying its HLS task does not enable this scratch-only recovery. Retain the old assets. Recovery needs a new validated archive rendition; no published-file migration or old-asset rewrite is performed. The normal source refresh/checkpoint path and matching selected-format fingerprint reuse existing media. There is currently no dedicated force-rearchive or legacy-repair button; do not describe a refresh as repair or recommend deleting the old archive to bypass reuse. A dedicated recovery workflow and legacy status audit remain follow-up work.

Useful diagnostic states are: **elementary Atmos detected**, **JOC container verified**, **legacy/unverified**, and **device output unverified**. Only the first two are media evidence; neither proves physical Atmos playback. No new legacy-status UI or automatic library scan is claimed here.

## Playback boundary and verification

The player prefers native HLS when the media element reports HLS support and retains custom HTML controls. Other engines may use hls.js or a separate available compatibility copy. The single muxed HLS media playlist does not emit a master `CHANNELS="n/JOC"` entry. A future multivariant master must follow the [Apple HLS appendix](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices-appendixes) using the measured JOC complexity; it must not guess `6/JOC` or `16/JOC` for every file.

The offline regression suite runs with networking disabled and read-only source samples. It validates original EC-3/JOC retention, actual merge/HLS output, packet hashes, source-file immutability, malformed boxes, chunk offsets and cancellation. Windows browser layout tests do not validate physical macOS/iPhone/iPad decoding, Bluetooth/HDMI/headphone routing or Dolby Atmos output. See [player device notes](../../../frontend/src/player/IOS_NOTES.md).

On 2026-10-05 the failed capture's complete unpublished merge (950,159,271 bytes; 331.936 seconds) was copied from a read-only scratch mount into an isolated, network-disabled container. Verification restored the measured JOC complexity 16 for its 8-channel EC-3 track; both audio and video packet hashes were identical before and after, and the original scratch file's whole-file SHA-256 remained unchanged. Separate regression cases cover a fresh merge and reuse of a previously completed merge. This verifies container signaling and media preservation, not hardware Atmos output.

The subsequently published original is 950,159,273 bytes (the restored JOC extension adds two bytes). A full offline HLS packaging test exposed a separate probing issue: the high-bitrate 4K HLS playlist initially reported only the 6-channel AC-3 core, although a small-video rendition with the same audio reported all 8 channels. [FFprobe format options](https://ffmpeg.org/ffprobe-all.html#Format-Options) document defaults of 5,000,000 probe bytes and 5,000,000 microseconds of analysis. On the identical full HLS package, one bounded probe at 33,554,432 bytes and 10,000,000 microseconds reported E-AC-3/Atmos, 8 channels and 7.1 correctly; both full audio and video packet hashes matched the source.

HLS verification now makes that single bounded retry only when an E-AC-3 channel count/layout differs. It then runs all existing stream-field, JOC, DOVI, duration and packet-hash checks unchanged. A persistent channel mismatch or missing/changed dependent audio packets still rejects publication. The full-package regression verifies the real 331.936-second published original through a read-only mount, including original SHA-256 immutability; no container label is accepted in place of the packet checks.

Optional SDR compatibility generation and lossless HLS are separate jobs (`create_playback` and `prepare_media`). The former reports `compatibility: unsupported`, `reason: hdr_conversion_unsupported`, and no rendition ID for the known unsupported HDR/wide-gamut conversion; it does not claim an SDR copy exists or relabel the successful original as a failed download. HLS still uses the original video/audio without tone mapping or AAC substitution. Other compatibility failures remain failures.

## Separate AAC audio compatibility rendition

EC-3 audio no longer requires an HDR-to-SDR conversion to obtain a playable audio alternative. For H.264, HEVC or AV1 pictures with EC-3 audio, `ensure_playback_variant` creates a separate `video-copy-aac-v1:<archive asset>` rendition before the SDR-only branch: video uses stream copy, while audio is decoded and downmixed to AAC-LC stereo at a target 192 kbit/s. The [FFmpeg streamcopy documentation](https://ffmpeg.org/ffmpeg.html#Streamcopy) distinguishes per-stream copying from transcoding. This reduces encoding work, but the independent MP4 and optional HLS still store another copy of the video bytes.

The new rendition must preserve video codec/profile, pixel format, dimensions, color properties, the complete probed DOVI configuration and the full compressed video packet SHA-256. It rejects unknown Dolby Vision configuration, multiple video/audio tracks, invalid AAC profile/layout, non-finite duration, duration mismatch and changed picture payloads before publishing. FFmpeg uses `-strict unofficial`, `hvc1` for HEVC and `write_colr`; it never applies a video filter or tone mapping. Published source assets and their original Atmos/HLS renditions are unchanged.

Both the rendition's `metadata_json` and its measured video properties carry `compatibility_mode: audio_only`, `source_variant_id`, `video_stream_copy: true`, `audio_transcoded: true`, `audio_codec: aac`, `audio_channels: 2`, `dolby_atmos: false` and an empty `ec3` object. Dolby Vision/HDR describe the actual preserved picture. An HLS package derived from this rendition retains those facts and refers to that AAC rendition as its source; it must never be confused with the archive's EC-3 package. The original SDR conversion path still reports unsupported for HDR sources that do not use this EC-3 audio-only path.

Apple's [HLS authoring requirements](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/) require a stereo AAC-compatible option; the [audio compatibility appendix](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices-appendixes/) lists AAC stereo across its device groups and distinguishes multichannel support from the actual output route. This implementation is a separately selected rendition, not a full multivariant audio-group/master implementation or a claim of universal device compatibility. Preserving HEVC/AV1, Dolby Vision and HDR means the device still needs the corresponding video support. The AAC sound is lossy stereo, never Atmos; spatial-audio capability alone is not grounds to switch away from a working EC-3 stream.

Offline tests on 2026-10-05 use read-only real 6-channel and AC-3-core/dependent-EC-3 8-channel sources, each bounded to a new 3-second scratch fixture paired with actual Dolby Vision video. AAC conversion and subsequent fMP4 HLS both passed: video packets/DOVI were preserved, AAC was stereo, Atmos labels were false, and the full original sample hashes were unchanged. A generated EC-3 test runs without private samples in CI; negative tests reject changed video packets, color/DOVI, invalid audio and additional tracks. No business task was retried and no original asset was rewritten for these tests. Physical macOS/iPhone/iPad playback and audio-route output remain unverified.
