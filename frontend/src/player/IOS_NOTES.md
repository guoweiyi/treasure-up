# Inline playback and iOS

This player keeps `HTMLVideoElement`, Artplayer controls and the danmaku overlay in the same page. The media adapter sets `playsinline`, the legacy `webkit-playsinline` attribute, and `controls = false` before assigning the source. Mobile settings use our own bottom sheet and radio buttons. Opening settings does not enter fullscreen. Webpage fullscreen remains available when element fullscreen is not exposed.

The adapter asks the actual video element whether it can play HLS and prefers that native path whenever available, without a Safari user-agent test. This does not enable the browser's native control bar. Other supported browsers use hls.js. A native video fullscreen surface or picture-in-picture window cannot be assumed to include the page's danmaku and custom controls.

Official references checked on 2026-10-04:

- [WebKit: New video policies for iOS](https://webkit.org/blog/6784/new-video-policies-for-ios/) documents inline playback with `playsinline`; playback with sound remains subject to user interaction policies.
- [Apple: allowsInlineMediaPlayback](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/allowsinlinemediaplayback) documents the additional native host setting needed by an embedded WKWebView. Website code cannot change a host application's configuration.
- [WebKit features for Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/) describes fixes involving WebVTT cues, fullscreen subtitles on iOS and `currentTime` update frequency. These release notes do not promise that every archived codec or HDR combination can play on every device.
- [bilibili/ijkplayer](https://github.com/bilibili/ijkplayer) is a native Android/iOS FFmpeg player, with platform decoders including VideoToolbox. Its documented iOS support and build prerequisites are historical; it is not a web media engine or evidence of iOS 27 compatibility. The useful design distinction is the separation of media decoding and playback UI.
- [bilibili/flv.js](https://github.com/bilibili/flv.js) transmuxes FLV to fragmented MP4 through Media Source Extensions. The project states that maintenance is infrequent. It is not a universal codec decoder and adds no required capability to this archive's existing MP4/HLS path.
- [bilibili/DanmakuFlameMaster](https://github.com/bilibili/DanmakuFlameMaster) is an Android danmaku parser and renderer using native views, including SurfaceView and TextureView. Its XML parsing and layout concepts are relevant; the engine cannot run directly in a web page.
- [xqq/mpegts.js](https://github.com/xqq/mpegts.js), linked by flv.js for live playback, targets low-latency MPEG-TS/FLV streaming. It is outside the bilibili organization and does not justify replacing this on-demand archive player.

The native shell's `Cargo.lock` pins Wry 0.57.0. Its [versioned WKWebView initialization](https://github.com/tauri-apps/wry/blob/wry-v0.57.0/src/wkwebview/mod.rs#L330-L331) already enables `allowsInlineMediaPlayback` for iOS. The current ordinary `WebviewWindowBuilder` therefore inherits this setting; no extra native builder override is needed for this dependency version. Recheck the setting when changing the native engine or supplying a custom WKWebView configuration.

## EC-3 and Atmos

Archive metadata describes the saved media, not the active audio output. The capture and new HLS pipeline preserve EC-3 packets and verify JOC configuration separately; the FFmpeg 7 limitation and treatment of old archives are documented in [Atmos preservation](../../../backend/app/playback/ATMOS.md). AAC compatibility copies remain separate assets and never replace the original EC-3 archive or inherit its Atmos label.

The player makes bounded `MediaCapabilities.decodingInfo()` queries using `audio/mp4; codecs="ec-3"` and measured channel/sample-rate/bitrate values when present. Native HLS and file playback use `type: "file"`; hls.js uses `type: "media-source"`. Support for one path is not copied to the other. Missing APIs, malformed results, exceptions and timeouts remain unknown. A response from a previous attachment cannot update the new video's state. Ordinary EC-3 decoding support is not spatial-output support: a spatial result is shown only when the result echoes the requested decoding type and `configuration.audio.spatialRendering === true`. Even that is labelled as device-reported capability with actual output unverified.

Unsupported or unknown EC-3 capability is visible next to the player and in settings, with an explicit action when an AAC audio-only copy of the selected original is already stored. This action never chooses a different original or quality. Such a copy must declare `source_variant_id`, `compatibility_mode: "audio_only"`, `video_stream_copy: true`, `audio_transcoded: true`, AAC stereo and `dolby_atmos: false`. The interface explains that video packets are preserved while audio is converted and is not Atmos. When no copy exists, viewers are told to ask an administrator to create it. Capability predictions do not block playback or silently override a manual selection; unsupported spatial rendering alone does not imply EC-3 decoding failure. A successful query or an Apple user agent is never used as evidence of actual Atmos output.

Separately, an actual HLS media/decode failure can fall back once to direct file playback of the same `source_variant_id`. This changes the transport, not video/audio quality. Route renewals then retain file mode. The existing bounded network retry is independent, and old asynchronous loads cannot attach or restore state after switching parts or versions. Position, pause/mute/volume/rate and initial autoplay intent survive recovery; autoplay refusal produces a user-action prompt rather than a false decoding diagnosis.

Playback settings also offer explicit file playback for audible faults that do not raise a media error. It retains the selected source variant and uses the existing recovery state restoration. An explicit file preference wins over a network recovery from an older HLS attachment; selecting automatic playback clears the previous protocol fallback. Once a revised AAC stereo copy (`audio_mix_revision: 2`) is explicitly generated, the shortcut prefers it over the old copy of the same original. Old copies stay selectable and are labelled separately. See the [audio crackle audit](../../../docs/incidents/2026-10-05-audio-crackle.md) for reproduced defects, tests and device limitations.

- [W3C Media Capabilities](https://www.w3.org/TR/media-capabilities/) defines the decoding and spatial-rendering query. Some implementations ignore unsupported configuration members; a successful ordinary decode query is insufficient evidence for Atmos.
- [Apple HLS authoring appendixes](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices-appendixes) use `ec-3` and `CHANNELS="n/JOC"`; `n` is the JOC complexity index, not the ordinary channel count. The present archive serves a single muxed media playlist and does not manufacture a multivariant master or claim full Apple authoring-profile compliance.
- [Apple HLS authoring requirements, audio section](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/) distinguish stereo fallbacks from Dolby formats and provide platform-specific qualifications. An AAC copy helps audio compatibility but does not make every device capable of decoding the preserved HEVC/AV1, Dolby Vision profile, resolution or frame rate. The same applies inside the native system WebView; no codec or Atmos-output privilege is added by the shell.

The 2026-10-05 automated capability/recovery checks cover native versus MSE queries, an ignored or mismatched spatial configuration, unavailable/timed-out APIs, stale probe responses, explicit original-to-AAC provenance, no protocol loops, source identity checks, late-switch cancellation and startup/pause restoration. They are browser API mocks and do not constitute physical iPhone, iPad, Mac or Atmos-output validation. The shell's existing inline WKWebView setup and origin/IPC isolation are unchanged; it does not add a native decoder or export browser credentials.

Custom controls, settings and queue navigation provide 44 CSS-pixel touch targets on coarse-pointer devices, including landscape and iPad split views. The sheet uses dynamic viewport height and fullscreen safe-area insets. This follows [Apple's button guidance](https://developer.apple.com/design/human-interface-guidelines/buttons) and [layout/safe-area guidance](https://developer.apple.com/design/human-interface-guidelines/layout); CSS emulation is not a physical-device measurement.

Automated tests cover the inline attributes, disabled native controls, bottom danmaku margins and missing bitrate handling. Desktop-browser viewport testing is not real iOS testing. A physical iPhone running iOS 27 is still required to validate user-gesture playback, rotation/safe areas, seeking, background return, subtitles, fullscreen transitions and hardware codec support.

Browser verification on 2026-10-04 used Windows Chrome at 1280×800 and 390×844. Actual playback advanced at 1.5× with native controls disabled; the inline attribute was present. Custom speed/settings sheets, danmaku defaults, webpage fullscreen, Escape/focus restoration, part switching and the mobile part list were exercised. Guest starring navigated to login with the original video as `next`; authenticated starring and reversal succeeded. Publication time, contributor roles, source/archived format labels and descending comment likes were checked with synthetic metadata around an existing local archive asset. The temporary fixture, its progress/sessions and derived maintenance jobs were removed; the original video and asset were confirmed present afterward.

The later Atmos/mobile iteration was checked in Windows Chrome at its desktop viewport, 390×844 and 320×740: the 320px sidebar's single-video mode has a visible label, the mode menu overlays following content, and the mobile settings sheet has no horizontal overflow. Playback preferences were unchanged and the viewport override was reset. These checks do not validate Safari/native HLS, physical touch targets, iPhone/iPad safe areas, macOS EC-3 decoding, or an Atmos-capable output route. Those remain real-device acceptance items.
